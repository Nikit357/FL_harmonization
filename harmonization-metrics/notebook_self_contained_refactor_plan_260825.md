# Making `correlation_prediction_metrics_analysis.ipynb` self-contained — plan (2026-08-25)

## Overview

The notebook fails at the first cell with `ModuleNotFoundError: No module named
'figures_helpers'`. The immediate cause is a wrong `sys.path` entry: `figures_helpers.py`
lives in `figures_for_article/figure_drawing_scripts/`, not in `figures_for_article/`.

```
$ find . -name "figures_helpers*"
./figures_for_article/figure_drawing_scripts/figures_helpers.py     ← the real file
./figures_for_article/__pycache__/figures_helpers.cpython-311.pyc   ← stale, from an older layout
./figures_for_article/.ipynb_checkpoints/figures_helpers-checkpoint.py
```

A one-line `sys.path` fix would make the notebook import again, but it would leave the
real problem in place: six opaque loader functions live in another directory, hardcode
their own input paths, and hide the filtering rules from the reader. `load_metrics_data()`
in particular defaults to `metrics_comprehensive_260609.csv` with no way to point it at
the current `metrics_comprehensive_260824.csv`, which is the table that actually carries
the L/M/N columns.

**Design decision: make the notebook fully self-contained, in the style of
`harmonization_metrics_analysis_v3.ipynb`.** Every input path becomes a named constant in
one setup cell; every filter, join and threshold is written out as explicit pandas code
in the cell where it is used. After this change the notebook imports nothing from the
repository — only stdlib and third-party packages — so `sys.path` manipulation disappears
entirely and there is no hidden default to be surprised by.

The notebook stays generated by `create_correlation_prediction_notebook.py` (per
`harmonization-metrics/CLAUDE.md`: regenerate rather than hand-edit). Inlining the loader
code into the generated cell strings is fully compatible with that; the generator is the
file that gets edited.

### The analysis set

Reproducing the v3 filter chain on `metrics_comprehensive_260824.csv`:

| Step | Rows |
|---|---|
| all rows | 3,835 |
| `status == "ok"` | 3,835 (every row is `ok` in this table) |
| drop Shambhala except `shambhala_P0std_Q0std` → renamed `20_shambhala` | 2,407 |
| `n_samples_allNA < 5,444 × 0.05` (drops `34_arsyn`, `38_harman`) | **2,234** |

Of those 2,234 rows, **2,150 carry blind-check metrics** and 84 do not. The 168 rows that
have blind-check metrics but sit *outside* the analysis set are exactly `34_arsyn` (84)
and `38_harman` (84) — the two methods excluded from Figure 3 for excessive NAs. The
current notebook includes them in every best-vs-rest boxplot, which is inconsistent with
Figure 3. Restricting `df_lmn` to the 2,234 analysis set fixes that.

Within the analysis set: 15 curated best rows (all 15 have `xb_rank_agree`), 84 `01_raw`
baseline rows (one per `strat × imp × post_rm`).

### Permutation counts — a real caveat

```
pv_n_perm within the 2,234-row analysis set:
  20.0 → 2,147 rows
  NaN  →    84 rows   (no Group N computed)
 100.0 →     2 rows
   5.0 →     1 row
```

The compute run used **20 permutations**, not the 100 the project `CLAUDE.md` command
line specifies. The empirical p-value floor is therefore `1/21 = 0.0476`, which sits just
below the `p = 0.05` line drawn in §8. Almost every point will land on that floor, and the
§8 panel will look like "everything is significant at exactly 0.0476". Three rows were
computed at a different `n_perm` and are not comparable to the rest.

This is a data fact, not something the refactor can fix. The plan adds an explicit
`PV_N_PERM_EXPECTED = 20` constant and a filter so the three odd rows are dropped from
p-value panels, and adds a note to the §8 markdown stating the floor. Whether to recompute
at `--n-perm 100` is Daniil's call and is listed as an open question below.

### Gene completeness — a silent bug

`filter_genes_complete_across_attempts(gene_long)` defaults to `min_frac=1.0`.

```
runs in gene_long: 2,318   genes: 554
genes with non-NA rho in ALL 2,318 runs:  0
genes with non-NA rho in >= 90% of runs:  178
```

It returns an **empty list**. The consumer then does `if genes_subset:` — an empty list is
falsy, so the filter silently does nothing and §3/§4 average over all 554 genes with
wildly different coverage. The 178 figure at 90 % matches
`marker_gene_coverage_audit_260819.csv` ("178 genes in all 42 pairs"), so 0.9 is the
threshold that reproduces the audit. The refactor makes this an explicit notebook
constant `GENE_MIN_FRAC = 0.9` and prints the resulting gene count, so an empty result can
never pass unnoticed.
